# レビューコメント記述仕様（SSOT）

本ドキュメントは、ExLibris リポジトリにおける Pull Request（PR）レビューおよび節目（Phase 完了・ミニリリース Milestone 完了）の全体横断レビューにおいて、人間レビュアーおよび AI エージェントが使用するコメントフォーマットの正本（Single Source of Truth）です。

---

## 1. 基本原則

1. **事実と証拠に基づく記述（Evidence-based）**:
   - 変更差分（diff）、変更対象ファイルの全文、承認済み仕様・設計正本（`docs/specs/`）、開発規約（`docs/guidelines/`）、テストコード、または実行証跡に裏付けられた具体的な問題のみを報告します。
   - 個人のスタイルの好みや、根拠のない推測的リスクを欠陥（Defect）として報告してはなりません。
2. **重要度（Severity）の明記**:
   - 各指摘には `[P0]` 〜 `[P3]` の重要度を付与し、重要度の高い順に並べます。
3. **再現・修正に必要な 4 要素の網羅**:
   - すべての指摘には「対象箇所（`Location`）」「問題内容と発生条件（`Problem`）」「正本との齟齬・影響（`Impact`）」「具体的な修正案・引き継ぎ（`Recommendation`）」の 4 要素を必ず含めます。

---

## 2. 重要度（Severity）の定義

| 重要度     | 名称                     | 定義・判定基準                                                                                                                                                                                    |
| :--------- | :----------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`[P0]`** | **致命的（Critical）**   | アプリのクラッシュ・VRAM OOM（`ImageBitmap.close()` 漏れ等）、ローカル DB データの破損・消失、重大なセキュリティ脆弱性、CI/開発環境の完全破損など、即座に対処が必要な致命的欠陥。                 |
| **`[P1]`** | **重大（High）**         | `docs/specs/` の受け入れ条件（`AC-xx`）やインターフェース/DB 契約の未達、ZIP/ZIP64 オフセット計算誤り、Task Completion Gate 違反（カバレッジ未達・1対1 Story/UT 欠落・原因 `D` の設計未同期等）。 |
| **`[P2]`** | **通常・改善（Medium）** | 基本機能は動くが設計整合性・保守性・型安全性を損なう問題、境界値・異常系の考慮漏れ、ドキュメント間の記述不整合やリンク切れ、OKF フロントマター不備。                                              |
| **`[P3]`** | **軽微（Low）**          | 将来の改善提案、軽微なタイポ・表記揺れ、可読性向上など、即座に修正しなくても動作や後続作業に影響を与えない事項。                                                                                  |

---

## 3. 単一指摘（Finding）の共通フォーマット

```markdown
### [重要度] 簡潔で具体的な要約

- **Location**: `path/to/file.ext:行番号`
- **Problem**: 不正な振る舞い・不整合な記述内容と、それが発生する条件。
- **Impact**: `docs/specs/` や `docs/guidelines/` との齟齬、システムや利用者への影響。なぜこれが誤りなのかの根拠。
- **Recommendation**: 具体的な修正方法、または後続 Issue（申し送り `HO-xx`）への引き継ぎ案。
```

---

## 4. PR レビューコメントの運用ルール

- **インラインレビューコメント**: 変更差分行に直接アンカーして上記フォーマットで投稿します。
- **PR 全体レビューコメント（指摘 0 件時のテンプレート）**:
  ```markdown
  ## レビュー結果

  - **確認範囲**: （対象 PR の変更ファイルおよび照合した `docs/specs/`・`docs/guidelines/`）
  - **実行した検証**: `npm run lint:okf`, `npm run typecheck`, `npm run lint`, `npm run test:coverage`, `npm run test:vrt` 等
  - **判定**: Actionable な指摘事項はありません。
  ```
- **スレッド返信と Resolve**: 実装者は各スレッドに修正コミット SHA（原因 `D` は設計同期 SHA 併記）を返信し、`pr-reviewer` が検証済みのスレッドのみを Resolve します。`pr-reviewer` 自身は PR の Approve や Merge、Issue クローズを行いません。

## 5. 節目横断レビュー（Phase / ミニMilestone 完了レビュー）の集約形式

### 5.1 指摘 ID（Finding ID）の採番ルール（ラウンドプレフィックス方式）

- **ID 形式**: `R<ラウンド番号>-<2桁連番>`（例: 初回は `R1-01`, `R1-02`、2回目は `R2-01` 等）
- **マルチモデル並行起動時の ID 衝突防止 3 原則**:
  1. **【原則1】レビュー開始時・検証中の既存コメント閲覧禁止**: 開始時や検証中は `gh issue view <issue-number> --comments` を実行せず、仮 ID `#1, #2...` で整理する。
  2. **【原則2】投稿直前（Just-in-Time）の最新コメント取得・重複照合・連番採番**: 全検証と下書きが完了し、投稿する直前に初めて `--comments` を取得し、先行指摘と同一内容は「先行指摘 `R1-xx` を追認・補強」とし、独自の新規指摘のみに先行最終 ID の次番を採番して即座に投稿する。
  3. **【原則3】投稿直後（Post-Submit）の衝突検知と自己コメント即時リナンバー**: 投稿完了直後に再度コメント一覧を取得し、数秒差で他エージェントと ID が衝突していた場合は直ちに `gh api --method PATCH` で自己コメント内の ID を連番へ振り直す。

### 5.2 横断レビュー集約コメントのテンプレート

```markdown
## 横断レビュー結果（Round N - レビュアー / モデル名）

- **対象フェーズ / Milestone**: （例: Phase 3 PoC / Milestone v0.1）
- **レビュアー種別 / 使用モデル**: （例: オーケストレーター #1 [Gemini Pro] / サブエージェント観点別検証）
- **対象成果物**: `docs/specs/`, `src/`, `test/it/`, `docs/quality/bug-and-handover-log.md`
- **対象 SHA**: `<commit-sha>`
- **確認した完了条件・ゲート**: （例: 要望 Issue #1〜#4 の完了、全テスト・VRT・カバレッジ 100% PASS）
- **実行したチェック**: （例: 独立サブエージェントによる観点別検証、静的検査・テスト実行確認）
- **先行コメントとの関係**: （例: 初回投稿 / 先行 R1-01〜R1-10 の追認および R1-11 以降の新規指摘起票）
- **未確認事項**: （例: 人間による実機最終確認・Milestone 承認は未実施）
```
